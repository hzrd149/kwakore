<objective>
Fix napplet windows that flash closed on Wayland (WebKitGTK's DMABUF renderer triggers "Error 71 (Protocol error) dispatching to Wayland display" and GTK exits 1) and make that class of failure diagnosable and visible.

Source: `.planning/research/WEBKIT-DMABUF-WAYLAND-REPORT.md`, all four report items selected by the user:
1. Log the window program's stderr and unexpected exit status (journal).
2a. The window program disables the DMABUF renderer on Wayland by default, with the opt-out `KWAKORE_WEBKIT_DMABUF=1`.
3. The real-engine WebKit tests stop masking the production renderer on Wayland.
4. An unexpected window death becomes user-visible through the existing `service.diagnostics` `recent_errors` path.

Purpose: today the child's stderr goes to the discard writer and `cmd.Wait()`'s result is dropped, so a crash looks like a normal "napp window closed". Non-Nix installs have no workaround for the Wayland crash at all.

Facts the executor needs (verified while planning, do not re-derive):

- linuxhost has no logger of its own. `backend.Logger()` (backend/backend.go:155) returns the backend's zerolog logger (set by `backend.Start`; the zero value is a disabled logger before Start). The daemon's log goes to stderr -> user journal and Debug is visible there (the report shows `DBG bridge rpc call`).
- The child's logger is `zerolog.New(zerolog.ConsoleWriter{Out: os.Stderr})` with a pid field `_` and a timestamp (desktop/child/main.go:55). ConsoleWriter colours its output even into a pipe (desktop/child/webkit_test.go strips ANSI with `\x1b\[[0-9;]*m`) and its default time format is `time.Kitchen` ("3:04PM"). So a child zerolog line on stderr looks like `<SGR>3:04PM<SGR> <SGR>INF<SGR> window program started _=1234 kind=napplet ...`. It is NOT JSON. Recognising "child zerolog lines" therefore means: after stripping SGR sequences, a time.Kitchen token followed by a space and one of the zerolog level abbreviations TRC DBG INF WRN ERR FTL PNC; additionally accept a JSON object line with a string `level` field. Do NOT change the child's log format: the real-engine tests match its console text.
- os/exec: `cmd.Wait()` closes the StderrPipe read end once the process exits (parentIOPipes), so all reads must finish before Wait, and calling Wait also unblocks a reader stuck because a grandchild still holds the pipe.
- `childTransport.Close()` (daemon stop, uninstall, shutdown) and `killAndWait()` (failed/timeout open) are the daemon-requested close paths; `readChild` also kills the group itself on a scanner error (overlong line); a `windowFailed` frame is the child reporting its own failure (already surfaced by the napplet-hardening notice).
- Launcher notices (`backend/launcher_notices.go`) are NOT exposed through the socket (docs/service.md "Known limitations"), so a notice would be invisible. `service.diagnostics` `recent_errors` (`DiagnosticError{category,time,detail}`, ring of 32, `Service.recordError`, backend/daemon/health_linux.go) already reaches users via `kwak diagnostics` and the TUI Diagnostics tab (prettyJSON). Categories are not allow-listed by the CLI or the protocol docs. Precedent for a reporter installed after `backend.Start`: `backend.SetNativeEntryReporter` in `daemon.Open`, cleared in `Service.Close`.
- `s.mu` is only held briefly (never across a launch), so calling `recordError` from the readChild goroutine cannot deadlock with a launch RPC.
- `desktop/child/harden_linux.go:287` has an empty Linux `prepareEngine()`; main.go calls `prepareEngine()` after `log` is set and before `webview.New` (GTK/WebKit init). `harden_windows.go` is the os.Setenv-before-init precedent. The child is built with CGO_ENABLED=1 and purego imports runtime/cgo, so `os.Setenv` reaches libc `getenv` used by WebKit and its subprocesses.
- WebKit treats `WEBKIT_DISABLE_DMABUF_RENDERER` set to "0" as "keep DMABUF", so "already present with any value" must be left alone (use lookup semantics, not empty-string checks).
- The host passes `os.Environ()` through to the child, so `KWAKORE_WEBKIT_DMABUF=1` on the user unit reaches the window program; the host env allowlist itself (KWAKORE_* keys + WEBVIEW_PATH) and its D-10 comment stay unchanged (TestLinuxHostChildEnvironment pins them).
- `TestRPCLinuxHostLaunch` (backend/daemon/rpc_linux_test.go:622) already launches a fake child that exits 0 on close, stops it, then rewrites the program to `exit 1` and expects launch to fail with Unavailable: the natural place for the daemon-side regression.
