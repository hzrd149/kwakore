# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Desktop Gio UI only (D-17: no Android UI, text or Kotlin work). This phase is mostly backend keying and registry work. Its UI is small and reuses the Phase 3 system (`03-UI-SPEC.md`): the notice stack, chip buttons, palette fields and spacing. It adds no new color tokens, fonts, icons or widget types. The surfaces are:

1. **S1. Napplet update confirmation** (D-14, KEY-07). It appears from the installed tiles, the napp page and the profile page. Napps keep their current one-click update.
2. **S2. Napplet uninstall confirmation**. This was added by this contract (UI-D3) because D-06 and D-24 make uninstall delete data and close windows.
3. **S3. "Unavailable — the latest version is invalid" state** (D-16, REG-01). It appears on discovery tiles and cards, on the napp page, in the profile list and on installed tiles.
4. **S4. Notices** in the Phase 3 stack:
   - the unsupported-`requires` warning (D-15, REG-04)
   - the trial-data-discarded warnings (D-09, D-25)
   - the trial failure error (D-13, REG-03)
   - the one-time "napplets need reinstalling" warning (D-01, D-23; UI-D7)
5. **S5. Store-window notice strip.** The store window renders the napplet-scoped notices from S4 so that store launches and Try clicks get visible feedback (UI-D5).
6. **S6. Try loading state.** A trial now downloads and verifies every `path` blob before it opens (D-13), so Try shows that it is working.
7. **S7. Background launch-time check** (D-19). It adds no new UI. It only drives the existing update state and the S3 unavailable state.

All sizes are Gio units: `unit.Dp` for spacing and dimensions, `unit.Sp` for text. 1dp = 1px at scale 1.

## Surfaces and Interaction Contract

**Focal points.** When a confirm dialog is up, the focal point is its title, then the destructive button. On a tile in the unavailable state, it is the status line, which replaces the missing action buttons. On the napp page of an unavailable napplet, it is the status block below the action row. In a notice stack, an error title comes before warning titles.

### S1 — Napplet update confirmation (D-14, KEY-07)

**Trigger.** It covers every napplet update entry point in the store window. Each one parks a confirmation instead of calling the backend:

| Entry point | Today | After |
|-------------|-------|-------|
| Installed tile or card "Update" (`desktop/store.go`, `installedUpdateBtns`) | `go backend.Update(id)` | napplet: open S1. napp: unchanged |
| Napp page "Update" (`detailUpdateBtn`) | `go backend.Update(n.ID)` | napplet: open S1. napp: unchanged |
| Profile list "Update" (`profileUpdateBtns`) | `go backend.Install(pn)` | napplet: open S1, confirming runs `go backend.Install(pn)`. napp: unchanged |

- The installed record's `IsNapplet()` decides napplet versus napp. For the profile path, the decision comes from `pn.IsNapplet()`.
- A click while `busy[id]` is ignored and opens no dialog.

**State.** It is desktop-only and lives in `storeState`. Use no backend `newPrompt`, because Android would render one (D-17). `confirm` holds `{kind: "update" | "uninstall", id, name string, target backend.Napp, viaInstall bool}`, and one confirmation exists at a time. Opening a second one replaces the first.

**Layout.** While `confirm` is set, the store window draws only the dialog. It replaces the header, the notice strip and the content, which is how the manager replaces its screen with the logout dialog. The dialog is `layoutConfirm(gtx, th, title, body, yesLabel, noLabel, yesBtn, noBtn, maxWidth)`, a generalization of `layoutConfirmLogout`:
- It is centered (`layout.Center`) on a `card` rounded rect (radius 10) with 20dp inner padding.
- Its vertical flex holds:
  1. the title (H6 20sp Bold, `fg`)
  2. 8dp
  3. the body (Body2, `subtle`, wraps, no `MaxLines`)
  4. 16dp
  5. the button row: the confirm button (destructive style, UI-D4), then 12dp, then the dismiss chip (`chipBg`/`chipFg`): "Keep current version" (S1) or "Keep napplet" (S2). `layoutConfirm` takes the dismiss label as an argument (`noLabel`); the logout call passes "Cancel", unchanged. Both use the default `material.Button` text size of 14sp, with `pointer.CursorPointer`.
- The text column is capped at 420dp in the store. `layoutConfirmLogout` becomes `layoutConfirm("Log out?", …, maxWidth 0)` with its existing copy.

**Interactions:**
- **Update** clears `confirm`, then runs `go backend.Update(id)`, or `go backend.Install(target)` when `viaInstall` is true. The existing busy state then shows "Working…" on the napp page's primary button.
- **Keep current version** clears `confirm`. Nothing else happens.
- **Stale guard:** each frame, before drawing, clear `confirm` without acting when any of these holds:
  - the napplet is no longer installed;
  - it is busy;
  - for `kind == "update"`, it no longer has `UpdateAvailable`, for example because the S7 background check found the latest version invalid.
- Closing the store window (`app.DestroyEvent`) clears `confirm`, so a reopened store never shows an old dialog.
- Update failures keep their existing `FetchErr` lines ("update failed: …").

### S2 — Napplet uninstall confirmation (UI-D3)

- The trigger is "Uninstall" on an installed napplet in three places: the installed tile or card (`uninstBtns`), the napp page primary button (`detailPrimaryBtn` while installed) and the profile list (`profileActionBtns` while installed).
- It uses the same `confirm` state (`kind: "uninstall"`), the same `layoutConfirm`, the same stale guard (it clears when the napplet is no longer installed or is busy) and the same window-close clearing as S1.
- **Uninstall napplet** clears `confirm`, then runs `go backend.Uninstall(id)`. **Keep napplet** clears it.
- Napps (35130) keep their one-click uninstall, unchanged.

### S3 — Unavailable state (D-16, REG-01, D-10)

**Data contract (backend → GUI).** `Napp.Unavailable string` (`json:"unavailable,omitempty"`).
- It is non-empty when the NIP-01 latest event for the address is invalid.
- It holds **one fixed reason phrase from the catalogue below**. It never holds a raw validator error, because several validator errors embed author text.
- It is set on entries in `Discovery`, `FetchAuthorNapps` results and address lookups.
- `Snapshot()` stamps it on `Installed` entries the same way it stamps `UpdateAvailable`. The persisted installed record stays the valid installed version.
- When `Unavailable != ""`, `UpdateAvailable` is always nil.
- An unavailable entry carries `Name` best-effort from its first `title` tag, sanitized: control and format runes stripped, whitespace collapsed, at most 64 runes.

**Reason catalogue (backend-owned, fixed strings, sentence case, no trailing period):**

| Validator failure class | `Unavailable` value |
|-------------------------|---------------------|
| `path` tags malformed, missing, duplicated, or no `/index.html` | `Its file list is malformed` |
| aggregate `x` does not match the `path` tags | `Its files don't match their hashes` |
| missing or malformed `d`, `x`, `title`, `server` tags; empty content; legacy tags; wrong tag counts | `Required tags are missing or malformed` |
| NIP-5D `source` not a valid git URL (D-11/D-18) | `Its source isn't a valid git URL` |
| malformed `i`/`z` tags, conventions or archetype contracts | `Its conventions are malformed` |
| anything else | `Its manifest is malformed` |

**Display name rule (desktop).** Wherever an unavailable entry's name is drawn, use `Name`, else `D`, else "Unnamed napplet". Run it through the sanitizer and `truncate(…, 32)`. Never fall back to `n.ID`, which is now the long `kind:pubkey:d` address.

**Discovery tile and card (and profile list card):**
- The icon (existing fallback), the name, the "napplet" chip and the author row render as they do today. The description is not drawn.
- Below the name block sits the **unavailable block**, with a top inset of 8dp in a tile and 4dp in a narrow card:
  - line 1 is the status: Body2 **Bold**, `danger`, "Unavailable — the latest version is invalid", `MaxLines = 2`;
  - 4dp;
  - line 2 is the reason: Body2 Regular, `subtle`, the `Unavailable` phrase followed by ".", `MaxLines = 2`.
- The card shows no "Try", "Install" or "Update" button. The card body stays clickable and opens the napp page. The author row still opens the profile.
- Discovery order and the kind/scope counts are unchanged. Unavailable entries are neither hidden nor sorted last.

**Installed tile and card (installed copy, latest event invalid):**
- It shows the same unavailable block, with a third line after another 4dp: Body2 `subtle`, "Your installed version still works."
- The description is not drawn while the block shows.
- "Open", "Settings" and "Uninstall" stay. There is no "Update" button, because `UpdateAvailable` is nil.

**Napp page:**
- When `Unavailable != ""`, the action row shows no Try, Install or Update.
- When the napplet is installed, Open, Uninstall (S2), Settings and Copy address remain. When it is not installed, only Copy address remains.
- Directly below the action row, with a top inset of 8dp, sits the status block on `bg`:
  - Body2 Bold `danger` "Unavailable — the latest version is invalid";
  - 4dp;
  - Body2 `subtle`, the reason phrase + ".";
  - when installed: 4dp, then Body2 `subtle` "Your installed version still works."
- The block takes the place of the "An update is available." line. Both never show together.
- The detail rows below are unchanged and show whatever fields the entry carries.

**Refusals behind the UI.** `TryNapplet`, `TryNappletFromDiscovery`, `Install` and trial promotion refuse unavailable entries:
- Try raises the S4 trial-failed notice with the "unavailable" detail.
- Install sets `FetchErr` "install failed: the latest version is invalid".

### S4 — Notices (Phase 3 stack, backend-owned copy)

All new notices use the existing `Notice{ID, Kind, Title, Detail, Path}` with `Path == ""`, the Phase 3 card layout and the "Dismiss" chip only. They are **session-only**: none is added to `DismissedNotices`, and `DismissNotice` persists only the keyring and state-corrupt ids, as today.

Author text inside notices (`{name}`) goes through a backend sanitizer equivalent to `napLinkLabel`: control and format (`Cf`) runes become spaces, whitespace is collapsed, and the result is cut to **48 runes + "…"**. Empty after sanitizing → `d` sanitized the same way → "Unnamed napplet". Domain tokens are already regexp-checked.

| Notice ID | Kind | Raised when | Slot / repeat rule |
|-----------|------|-------------|--------------------|
| `napplet-requires:<address>` | warning | `launchWindow` succeeded for a NIP-5D napplet with non-empty `MissingDomains()`. A WEB-NAPPLET `R`/`O` tag never raises it (WEB-NAPPLET MUST) | One slot per address. Every launch re-raises it, even after a dismissal, and replaces it in place |
| `trial-data-discarded:<address>` | warning | Trial promotion (accepted prompt, or the already-installed branch) discarded the trial data: different artifact hash (D-09) or a non-empty installed store with the same hash (D-25) | One slot per address. The newest outcome replaces the older one |
| `napplet-trial-failed` | error | A Try opened no window because a `path` blob failed download or sha256 verification (D-13), or the entry is unavailable (S3) | One shared slot. Each failure replaces it and re-raises it after a dismissal |
| `napplets-reinstall` | warning | The state load dropped one or more old-id (`napplet~pk16~d`) records (D-23). That load saves state, so this happens on one start only | Single slot. It is not raised again on later starts because nothing is left to drop |

**Display order** (`noticeRank`, extended; same rank keeps insertion order):
1. `child-unavailable`
2. `napplet-hardening`
3. `napplet-trial-failed`
4. `state-corrupt:*`
5. `keyring-fallback`
6. `napplets-reinstall`
7. `napplet-requires:*` and `trial-data-discarded:*`

**Cap.** At most **3** notices with the `napplet-requires:` or `trial-data-discarded:` prefixes are live together. Adding a fourth drops the oldest of them. Existing slots are replaced in place and do not count as new.

**Window raising:**
- None of these notices calls `showManager()`. A requires warning goes with a napplet window that did open, and raising the manager would steal its focus.
- Trial promotion happens in the manager prompt, which `PromptsChanged` already raises, so its notices land in the window the user is looking at.
- Store-originated notices also show in the store (S5).

### S5 — Store-window notice strip (UI-D5)

- **What renders:** the store window renders `layoutNotices`, filtered to the IDs `napplet-trial-failed`, `napplet-requires:*` and `trial-data-discarded:*`, in the backend order. Launcher-level notices (keyring, corrupt state, child-unavailable, hardening, reinstall) stay manager-only, which keeps Phase 3's UI-D2.
- **Placement:** a `layout.Rigid` block at the top of the store's content area, below the header and inside the existing 24dp side insets, above the list or page. The content below stays `Flexed(1)`. The strip spans the full content width on list views and on pages. It is not limited to `readableColumn`.
- **Same cards:** the cards are the Phase 3 cards: 8dp between them, 16dp below the last, and zero height when empty.
- **Hidden while a confirm is up:** while S1 or S2 is up, the strip is not drawn.
- **Widget state:** notice widget state becomes per-window. `noticeUI` turns into a type, and the manager and the store each own one, because the two windows run separate frame goroutines.
- **Dismiss:** "Dismiss" in either window calls `backend.DismissNotice(id)` and the card disappears from both.

### S6 — Try loading state (D-13)

- While `busy[id]` is true for an uninstalled napplet, every Try button for it reads **"Opening…"**: discovery tiles and cards, the napp page, and the profile list. It keeps its `suggestBg`/`suggestFg` style, and clicks are ignored. A Try is busy while the backend downloads and verifies every `path` blob.
- `layoutDiscoveryTab` receives the `busy` map for this.
- On the napp page the primary button shows the existing "Working…" at the same time. That is accepted, existing behavior.
- On failure, no window opens, `busy` clears, the `napplet-trial-failed` notice appears (S4/S5), and the discovery `FetchErr` line shows the fixed copy below. It never shows a raw error, URL or hash.
- On success, the window opens as today.

### S7 — Background launch-time check (D-19)

- It adds no new UI element: no spinner, no notice, no `FetchErr`. It does not set `UpdateCheckRunning`, so the manual ↻ button is not dimmed by it.
- Its only visible effects arrive through `Snapshot()` on the next `StateChanged()`:
  - an installed tile gains the existing "Update" button and the napp page gains its "An update is available." line; or
  - the S3 unavailable block appears and any "Update" button disappears. That also clears a pending S1 dialog through the stale guard.
- When it is offline, fails or times out, the previous state stays and the failure goes only to the log (Debug or Warn).
- A launch never waits on it.

## Decisions Made in This Contract

The upstream locks D-09, D-10, D-13, D-14, D-15, D-16, D-17, D-19, D-23, D-24 and D-25 are pre-populated above. The orchestrator ran with `--auto`, so these choices are the researcher's own, consistent with `03-UI-SPEC.md` and the existing Gio code:

- **UI-D1:** The update confirmation covers all three napplet update entry points, including the profile list's Update, which calls `Install`. KEY-07 says "the desktop update UI", and D-14 names only two of them. It is desktop state in `storeState`, not a backend prompt, so Android never renders it (D-17).
- **UI-D2:** `layoutConfirmLogout` is generalized into `layoutConfirm`, and both dialogs use it. Its geometry (20dp padding, radius 10, H6 title, 8/16/12dp gaps) is unchanged. The store passes a 420dp text cap.
- **UI-D3:** Uninstalling a napplet asks for confirmation. D-06 and D-24 make uninstall delete storage, settings and permissions and close open windows, which is new and destructive. Napps are unchanged. This is the only surface beyond the orchestrator's list. Dropping it does not affect any requirement.
- **UI-D4:** The destructive confirm button is filled with `danger` and labeled in `bg` (5.50:1 and 6.40:1). The current `danger` text on `chipBg` measures 4.49:1 in light mode, so the logout dialog changes with it.
- **UI-D5:** The store window renders a filtered notice strip (trial failure, requires, trial-data). Most Try clicks and many launches start in the store, and the manager stack would otherwise be out of sight. Launcher-level notices stay manager-only (Phase 3 UI-D2). No Phase 5 notice raises the manager window.
- **UI-D6:** `Napp.Unavailable` holds a fixed reason phrase from a 6-entry catalogue, never a raw validator error, because those embed author text. Unavailable entries show `Name`, else `d`, else "Unnamed napplet", never the raw `kind:pubkey:d` id.
- **UI-D7:** A one-start `napplets-reinstall` warning explains why old-id napplets vanished (D-01/D-23, no migration). It is session-only and fires only on the load that drops them.
- **UI-D8:** Requires warnings re-raise on every launch (spec-literal REG-04) in one slot per napplet. Together with the trial-data notices they are capped at 3 live.
- **UI-D9:** Try shows "Opening…" while busy, because D-13 makes a Try download and verify every path before the window opens. The backend `busy` map already tracks it.
- **UI-D10:** The backend trial prompt copy stays unchanged (shared with Android, D-17). The trial-data notice explains when the promise "keep the data" could not be met.
