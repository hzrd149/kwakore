    - Clearing one field exposes its current file value, or its documented default, without clearing other overrides.

Keep overrides in settings-overrides.json under the resolved XDG data directory, distinct from config.json and legacy state.json; never write config.json.   <behavior>
    - Validation failure makes no disk write and leaves active settings unchanged.
    - A failed atomic write before rename leaves the old file and active snapshot intact; an error after rename reconciles the active snapshot to the validated bytes actually on disk.
    - Existing override files with unknown, duplicate, malformed or trailing data fail startup; symlinked or other-owned override paths are refused.
  </behavior>
  <action>Harden the D-07 transaction boundary. Verify private owner-only data directory and regular override file before reading or writing; refuse symlinked targets and owner/mode mismatches so fileutil's rename cannot target an attacker-controlled location. Add an injectable write seam around fileutil.WriteFileAtomic for deterministic failure tests. Its post-rename directory-sync error can leave the new bytes on disk despite an error: after any ambiguous failure, re-read and strictly validate the actual file while holding the manager mutex and make the active snapshot match that durable observed record. If reconciliation cannot establish a valid record, mark persistence unhealthy and reject further changes rather than claiming the old state is still persisted. Test the before-rename and after-rename cases, malformed on-disk files, and concurrent independent-field writes. Never deserialize or serialize the broad AppState, which may contain login secrets.</action>
