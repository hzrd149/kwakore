Stop go-webview's embedded package from dropping libwebview into a shared temp dir, and load the same library bytes from the launcher's verified per-user dir instead (PROC-02).

Output: webviewlib package fed by a generate step, libwebview extraction through childbin, WEBVIEW_PATH wiring, child-side check, just and CI steps.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| other local users → /tmp and %TEMP% | can pre-plant libwebview where go-webview's embedded init used to write |
| parent env → child loader | WEBVIEW_PATH and the DLL search order decide which library the child maps |
| module cache → build | the copy step trusts the pinned go-webview module contents |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-18 | Elevation of privilege | shared /tmp/webview-0.12.0 dlopen | high | mitigate | embedded import removed; library extracted by childbin into the verified per-user dir (Task 1) |
| T-03-19 | Elevation of privilege | Windows DLL search via PATH prepend | high | mitigate | no PATH change; webview.dll next to the child exe in the user-only dir (Tasks 1-2) |
| T-03-20 | Tampering | bare-name dlopen fallback | medium | mitigate | child exits when the library is not at the absolute WEBVIEW_PATH / exe dir (Task 1) |
| T-03-21 | Tampering | copies drifting from the pinned module | medium | mitigate | sync_test compares bytes; go.sum pins module content (Task 3) |
| T-03-22 | Denial of service | Windows rename over a loaded DLL after upgrade | low | accept | fail closed with child-unavailable notice (Pitfall 2) |
