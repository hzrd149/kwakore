# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This is a hardening phase with a small UI surface, all of it in the Gio desktop **manager window** (`desktop/main.go`, `desktop/layout.go`, `desktop/login.go`). It adds three things:

1. **Notice stack**: dismissible banners for (a) keyring unavailable, so the login stays in a private file (D-12), (b) a corrupt `state.json` that was set aside (D-14), and (c) napp windows that fail closed because the child binary is missing or was tampered with (D-03).
2. **Keyring waiting and failure states** on the loading screen and the login screen (D-11). A keyring call can take up to 120 s. The UI never freezes and always tells the user what it is waiting for.
3. **Visible fail-closed window error** (D-03). A prod child that is missing or tampered with produces a visible error. It is never a silent no-op.

The phase adds no new colors, fonts, spacing values or widgets. Everything below reuses tokens and patterns that already exist in the desktop module. Android renders none of this. It ignores `State.Notices` and the keyring wait state (ANDR-02 is deferred).

All sizes are Gio units: `unit.Dp` for spacing and dimensions, `unit.Sp` for text. 1dp = 1px at scale 1.

## Spacing Scale

Declared values for this phase's new code (all multiples of 4, in dp):

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4dp | Gap between a notice title and its detail line; gap between detail and the path box |
| sm | 8dp | Gap between stacked notices; gap between buttons in a row; inner inset of the path code box; chip-button inset (`layout.UniformInset(unit.Dp(8))`, existing chip convention) |
| md | 12dp | Inner padding of a notice card (all sides); gap between a notice's text column and its buttons; gap between the loader and the loading text |
| lg | 16dp | Existing manager-window outer inset (`UniformInset(16)`, unchanged); gap below the notice stack before the screen content; gap above the button row on the keyring-failed screen |
| xl | 24dp | Loader diameter on the loading screen (a dimension, not a gap) |

Exceptions:
- 12dp is a declared step. The existing desktop code already uses it for card padding and section gaps (`renderNappCard`, `layoutMain`, `login.go`), and the new surfaces match it.
- Existing 6dp and 10dp spacers in untouched code (`layoutPrompt`, `login.go`) stay as they are. New code in this phase must not introduce 6dp or 10dp.
- Corner radii follow existing shapes: notice card **8dp** (same as `renderNappCard`), path code box **6dp** (same as the `layoutPrompt` code block).
- The text column has a max width of **420dp** on the loading screen only (same cap as the relay row in `login.go`).

## Typography

Gio material defaults with `th.TextSize = 16` (unchanged). Line height is Gio's default `LineHeightScale` of 1.2 for every role. Do not override `LineHeight` or `LineHeightScale`.

| Role | Size | Weight | Line Height | Gio call |
|------|------|--------|-------------|----------|
| Body | 14sp | Regular (400) | 1.2 (Gio default) | `material.Body2(th, …)`: notice detail, path, keyring waiting detail |
| Label | 13sp | Regular (400) | 1.2 (Gio default) | chip buttons with `b.TextSize = unit.Sp(13)`: "Dismiss", "Copy path", "Log in again" |
| Heading | 16sp | Bold (700) | 1.2 (Gio default) | `material.Body1(th, …)` with `Font.Weight = font.Bold`: keyring-failed screen title. Loading-screen lines use Body1 at Regular |

Notice titles use **Body (14sp) at Bold**. They are the same size as the detail, and only the weight changes. The primary "Try again" button uses Gio's default button size, which is 14sp (`th.TextSize*14/16`), so it shares the Body size.

Total for this phase: **3 sizes (16, 14, 13)** and **2 weights (Regular 400, Bold 700 via `font.Bold`, which selects `vb.ttf`)**. No italic in new surfaces.

| Role | Palette field | Value (light / dark) | Usage |
|------|---------------|----------------------|-------|
| Dominant (60%) | `bg` | `#ffffff` / `#17181b` | Manager window background (existing `paint.Fill(gtx.Ops, pal.bg)`) and the loading screen |
| Secondary (30%) | `card` | `#f2f2f2` / `#23252b` | Notice card fill |
| Secondary text | `fg`, `subtle` | `#000000`/`#e8e8ea`, `#666666`/`#a0a4ad` | Warning notice title (`fg`); every notice detail line and the keyring waiting detail (`subtle`) |
| Code box | `codeBg`, `codeFg` | `#f0f0f0`/`#21232a`, `#333333`/`#cfd2d8` | Path box inside the corrupt-state notice |
| Chip | `chipBg`, `chipFg` | `#e8e8e8`/`#2b2e35`, `#333333`/`#d8d8dc` | "Dismiss", "Copy path", "Log in again" buttons |
| Accent (10%) | `contrastBg` / `contrastFg` | `#3f51b5` / `#5c6bc0` (text `#ffffff`) | Only the elements listed below |
| Destructive | `danger` | `#cc2222` / `#ff6b6b` | Error-severity notice title only (child unavailable) |

Accent is reserved for:
1. The `material.Loader` spinner on the loading screen (its default color is `th.Palette.ContrastBg`).
2. The "Try again" primary button on the keyring-failed screen (default `material.Button`).
3. The existing "Log in" primary button on the login screen (unchanged; only its label changes while waiting).

Accent is never used for notice cards, notice text, or the "Dismiss", "Copy path" and "Log in again" buttons, which are chip-styled.

Severity mapping (no new color tokens):
- **warning** (keyring fallback, corrupt state): `card` fill, title in `fg` at Bold, detail in `subtle`.
- **error** (child unavailable): `card` fill, title in `danger` at Bold, detail in `subtle`. This matches how every existing error line is drawn (`LoginErr`, `shortcutErr`, `FetchErr`: `danger` on Body2).
- Do not use `devBg`/`devFg` (means "napp you are working on") or `suggestBg`/`suggestFg` (means "your usual choice") for notices.

Contrast checks (WCAG 2.1 AA for body text, ≥4.5:1):
- `subtle` on `card`: 5.13:1 light, 6.13:1 dark.
- `danger` on `card`: 4.91:1 light, 5.52:1 dark.
- `codeFg` on `codeBg`: 11.09:1 light, 10.36:1 dark.
- `fg` on `card`: well above 4.5:1 in both themes.
- These are computed for the built-in light and dark palettes. Omarchy/system overrides are not re-checked by this phase.

## Surfaces and Interaction Contract

**Focal points:** on the main and login screens, an error-severity notice title when present, otherwise the existing content; on the loading screen, the loader, or the failed title and "Try again" when the keyring wait has failed.

### S1 — Notice stack (manager window)

**Data contract (backend → GUI, pull-based via `Snapshot()`):**
- `State.Notices []Notice`, where `Notice{ID, Kind, Title, Detail, Path string}`, `Kind` ∈ `"warning"`, `"error"`. The backend owns the copy (constants in a `launcher_notices.go`-style file), and the desktop renders `Title`, `Detail` and `Path` verbatim.
- `backend.DismissNotice(id string)` is called from the frame handler. It updates state and calls `notifyState()`. Persisted dismissals live in `AppState.DismissedNotices` (D-12).
- Fixed order, at most one notice per ID: **error (child-unavailable) → corrupt-state → keyring-fallback**. The stack holds at most 3 notices.

**Where it renders:**
- At the top of the manager window's content area, inside the existing 16dp window inset, in both `PhaseLogin` (above the "Log in to Verdana" / "Connect a signer" title) and `PhaseMain` (above the profile row). It stays visible while the bundle-shortcut editor is open.
- It does not render during `PhaseLoading`, while a launcher prompt (`layoutPrompt`) takes over the window, or while the "Log out?" confirmation is up. The store window never shows notices.
- It is a `layout.Rigid` block. The existing content below it stays `layout.Flexed(1)`, so lists keep scrolling in the remaining height.

**Notice card layout:**
- Card: `clip.RRect` radius 8dp, `paint.Fill(card)`, full available width, inner inset 12dp on all sides (same record/replay pattern as `renderNappCard`).
- Horizontal flex, `Alignment: layout.Start`:
  - `Flexed(1)` text column: the title (Body2 Bold; `fg` for warning, `danger` for error), then 4dp, then the detail (Body2 Regular, `subtle`). If `Path != ""`: 4dp, then the path box (6dp radius, `codeBg` fill, 8dp inset, Body2 in `codeFg`, `WrapPolicy = text.WrapGraphemes` so the path wraps anywhere and is **never truncated**).
  - 12dp spacer.
  - `Rigid` button row: for corrupt-state, "Copy path" chip, 8dp, "Dismiss" chip. For the others, the "Dismiss" chip only. Chip style is `chipBg`/`chipFg`, 13sp, inset 8dp, `pointer.CursorPointer` (same as the existing `chip()` helper in `login.go`).
- Notices are separated by 8dp. 16dp sits below the last notice. When `len(Notices) == 0`, the stack draws nothing: zero height and no spacer.
- Titles and details have no `MaxLines`. They wrap.

**Interactions:**
- **Dismiss** calls `backend.DismissNotice(id)` and the card disappears on the next frame. It does not delete any file.
- **Copy path** (corrupt-state only) runs `gtx.Execute(clipboard.WriteCmd{…})` inside the frame (same as `loginScreen` "Copy connect link") with the full path. After a successful copy, the chip label reads "Copied" for the rest of the process.
- Clicking the card body does nothing.

**Per-notice lifecycle:**

| Notice ID | Kind | Shown when | Dismissal |
|-----------|------|------------|-----------|
| `keyring-fallback` | warning | Desktop only (`Options.Secrets != nil`), a login exists, and secrets are in file mode because the keyring was unavailable or timed out (`SecretsLocation == "file"` after a failed probe, Get or Set). Never on Android, never in tests with nil `Secrets` | Persisted in `DismissedNotices`; stays hidden across restarts while the fallback persists. Cleared when secrets move into the keyring, so a later fallback shows it again |
| `state-corrupt:<unix>` | warning | A `state.json.corrupt-<unix>` copy was set aside (D-14). Shows on every start until dismissed. If more than one exists, only the newest is shown | Persisted in `DismissedNotices` under its full ID. A new corruption gets a new ID and shows again |
| `child-unavailable` | error | A napp window, napplet window or settings window failed to open because the prod child binary (or libwebview) is missing or failed hash verification (D-03) | Session only, not persisted. Every new failed open re-adds it even after a dismissal; a repeat failure while it is already showing does not add a second copy |

### S2 — Fail-closed window error (D-03)

- In prod builds, `childExePath()` returns an error instead of falling back to `./child/child`. `startChild`/`startSettingsChild` return it, so the window never spawns.
- The backend sets the `child-unavailable` notice. The desktop then calls `showManager()` so the manager window opens or is raised and the notice is visible, even when the open came from a shortcut click, the tray or the store.
- Existing paths keep their error lines: a `Launch` from the store still sets `FetchErr` ("launch failed: …"), which the store draws in `danger` under its header. `OpenLauncherSettings` failures, which today only log at Warn, now also produce the notice.
- The error is logged at Error with the cause (missing, hash mismatch, ownership or permission) and the path. The UI copy stays generic and does not show hashes.
- Dev builds keep their on-disk fallbacks and never show this notice for a missing embedded child.

### S3 — Loading screen with keyring wait (`PhaseLoading`, D-11)

**Data contract:** a new `State.KeyringWait string` ∈ `""` | `"waiting"` | `"failed"`, plus `backend.RetryKeyring()` and `backend.LoginWithoutKeyring()` (the latter moves the launcher to `PhaseLogin` and does not touch the keyring item). Keyring calls always run off the UI goroutine. The frame loop only reads `Snapshot()`.

- `"waiting"` is set only after a keyring call has been in flight for **1 s**, so a fast unlock never flickers. It is cleared when the call returns or times out.
- `"failed"` is set only when the call failed or timed out **and** the secrets live only in the keyring (`SecretsLocation == "keyring"`, so there is no file copy). In every other failure case the backend falls back to the file copy, continues to `PhaseMain`, and raises `keyring-fallback`.

**Layout:** `layout.Center`, a vertical flex, children centered, text column capped at 420dp, `Alignment = text.Middle` on labels.

| State | Content (top to bottom) |
|-------|------------------------|
| `""` | `material.Loader` 24dp (accent) · 12dp · Body1 "Loading…" (replaces the current bare "Loading…" label) |
| `"waiting"` | Loader 24dp · 12dp · Body1 Regular waiting title · 4dp · Body2 `subtle` waiting detail |
| `"failed"` | No loader · Body1 **Bold** failed title (`fg`) · 4dp · Body2 `subtle` failed detail · 16dp · row: "Try again" (`material.Button`, accent) · 8dp · "Log in again" (chip, 13sp, inset 8) |

- **Try again** calls `go backend.RetryKeyring()`. The state goes back to `""`, then to `"waiting"` after 1 s.
- **Log in again** calls `go backend.LoginWithoutKeyring()`. The saved keyring login is not deleted. A new login made on the login screen replaces it only when the new login is saved.
- `material.Loader` invalidates its own frames. Nothing else on this screen needs a ticker.

### S4 — Login screen while a keyring write is pending (`PhaseLogin`, D-11)

- This uses the same `State.KeyringWait`. In `PhaseLogin`, `"waiting"` means a successful login (nsec, bunker, or a scanned nostrconnect) is saving its secrets and the keyring is slow or showing an unlock prompt.
- While `"waiting"`, the "Log in" button label reads "Waiting for keyring…" and its clicks and submits are ignored. The editor stays editable. On the nostrconnect view, the buttons are unchanged.
- In the position of the `loginErr` line (12dp top inset, both views), it shows the Body2 `subtle` login-waiting line instead of an error.
- A timeout or unavailable store during the save falls back to file mode (no `"failed"` state on the login screen). The launcher continues to `PhaseMain`, and the `keyring-fallback` notice appears there.

## Decisions Made in This Contract

Upstream locks D-03, D-11, D-12 and D-14 are pre-populated above. The orchestrator ran autonomously, so these choices are the researcher's own, consistent with the existing Gio UI:

- **UI-D1:** Notices reuse the `card` fill with an 8dp radius and 12dp padding (the napp-card shape). Severity shows only through the title color (`fg` vs `danger`). No new color tokens, glyphs or left-edge bars.
- **UI-D2:** Notices render on both the login and main screens of the manager window. This is needed because a corrupt `state.json` usually drops the user onto the login screen. They are hidden during loading, prompts and the logout confirmation. The store window does not render notices.
- **UI-D3:** Notice copy is owned by the backend (`Notice.Title/Detail/Path`), and the desktop renders it verbatim. The `keyring-fallback` notice is emitted only when `Options.Secrets != nil`, so Android and tests never see it.
- **UI-D4:** `child-unavailable` is session-only and re-raised on every failed open, together with `showManager()`, so a shortcut or tray launch never fails silently.
- **UI-D5:** One `State.KeyringWait` field drives both the loading screen and the login screen. It flips to `"waiting"` only after 1 s, to avoid flicker. `"failed"` exists only when the secrets live solely in the keyring.
- **UI-D6:** The keyring-failed screen offers "Try again" (primary) and "Log in again" (an escape hatch that never deletes the keyring item), so a missing Secret Service (Hyprland or sway without one) is never a dead end.
- **UI-D7:** The existing bare "Loading…" label gains a 24dp `material.Loader`, which proves the UI is live during the up-to-120 s unlock wait.
- **UI-D8:** Only the corrupt-state notice has an extra action ("Copy path"), because its path is long and the user needs it to recover data by hand.
