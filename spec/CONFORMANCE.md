# Verdana napplet runtime conformance

This is the audit checklist for Verdana's napplet runtime. It measures the
launcher against the exact spec texts committed in [`pinned/`](pinned/README.md),
at the commits recorded in `.planning/research/SPEC-PINS.md`. It is a public
claim about what the runtime guarantees, so every claim here points at code
and a test.

## How to read

Each pinned spec has its own section, headed `{spec} @ {full commit}`, in the
same order as `pinned/README.md`. Its table has the columns
ID | Requirement | Level | Status | Reason | Code.

Status values:

- **conforming**: the runtime already does what the text requires.
- **fixed (Phase N)**: the runtime did not conform and phase N changed it.
- **N/A**: the requirement does not apply to Verdana; the Reason cell says why
  (often a Conflicts row).
- **open**: not met yet. The Reason cell names the owner phase and requirement.

Rows with the Level **Non-Guarantee** (`5D-NG-*`, one per webview engine)
record what NIP-5D's Non-Guarantees leave to the browser. Their Status is
N/A, and their Reason cell says what was measured on that engine and what is
still unverified. A behavior is claimed for an engine only after a recorded
run on it.

Every row whose status is fixed cites the code symbol and the test that
implement it in the Code cell. `backend/spec_conformance_test.go`
(`TestConformanceChecklistSkeleton`) fails if a fixed row has an empty Code
cell.

Row IDs reuse the gap ID from `.planning/research/FEATURES.md` when a row
matches a gap (`5D-1`, `5D-3`, `W-1`). Other rows are `{SPEC}-{n}` or
`{SPEC}-{topic}`. Conflict IDs (`A1`-`A23`) and dropped-patch IDs (`P1`-`P7`)
are stable, so later phases and commits can cite them.

Text in “curly quotes” is verbatim from a pinned snapshot. The snapshots are
hard-wrapped in places; a quote joins those line breaks with a single space and
is otherwise exact. `TestConformanceChecklistSkeleton` checks every curly-quoted
passage in these tables against the snapshots.

Phase 1 writes the sections, the Conflicts, the dropped shim patches, the
decisions and its own rows. The domain phases add their rows as they land, and
Phase 8 (SPEC-02) closes every section so each shell-applicable MUST and SHOULD
has a row.

## Decisions

| ID | Decision | Reason | Owner |
|----|----------|--------|-------|
| DEC-1 | Accept upstream's 30 s per-request shim timeout (5 s for storage). Go still answers late and the shim ignores the late reply. A permission prompt still open after the napplet's request timed out is cancelled and treated as dismissed, so the user never approves an action whose result the napplet has given up on (D-10) | The shim is vendored unmodified (P1); prompts must not outlive the request they serve | Phase 2 DISP-04, inside the bounded prompt queue (D-11) (implemented: per-route deadlines 30 s, 5 s storage, promptTimeout for relay publish and upload; TestPromptCancelledAtRequestDeadline) |
| DEC-2 | `notify.controls` is pushed on the first load event of each frame (`nap.loaded`, napLoaded), on the assumption that `load` fires after the napplet's top-level scripts. A document that replaces the frame's own (a reload, a navigation) is a new frame with a new session (Phase 4, `NIP-5D-reload`), so every document gets the push exactly once. Fallback trigger if a webview breaks that assumption: the first `notify.*` envelope of the session | NAP-SHELL's `shell.init` used to carry the push and is gone (A18); upstream `onControls` has no replay (P5) | Phase 1 (done); one push per frame since Phase 4 (`backend/webview/napplet-host.js` boot; TestNappletHostRebuildsReplacedFrame); the real-webview check is on the phase smoke list |
| DEC-3 | Android pull-request CI binds only the gomobile AAR (D-17); the full APK builds on `workflow_dispatch` and `v*` tags | Keeps PR CI fast and path-filtered. Residual risk: a Kotlin compile break caused by a `backend/mobile` API change surfaces only on dispatch/tag APK builds | Phase 1 (done, SPEC-05) |
| DEC-4 | A prompt answer that arrives over a window's wire (`promptAnswer`) is accepted only for a prompt shown over that same window. Prompts the launcher raises itself (`Instance` empty, such as install confirmations) are answered only from the launcher's own UI, never from a window. Prompt ids are random, not serial. On desktop a bridge napp's page no longer gets an untokened `__verdana_prompt_answer`: the overlay answers through a binding that demands a per-window token, carried only by the overlay code. Residual: a bridge napp's overlay is still drawn inside the napp's own document, so the napp can click (or script) the answer to its own prompt | Without the owner check any napp could approve another napplet's `approve`/`grant` prompt, or a launcher prompt, with "always" (Phase 2 review CR-01) | Phase 2 (done: `backend/window_prompt.go` handlePromptAnswer, newPromptID; `desktop/child/main.go` bridgeAnswer; test TestPromptAnswerOnlyFromOwner). The residual in-page overlay is Phase 8 (trusted prompts) |
| DEC-5 | The launcher preamble posts one document-start message (`{type: "__verdana.document"}`, DocumentMarker) to the parent after `install`, inside the same function scope as the prelude and before any napplet script runs. It adds no global and leaves the shim bytes and the napplet bytes untouched.
